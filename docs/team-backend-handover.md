# 숭실한장 main 반영 내용 및 백엔드 인수인계

작성 기준: 2026-11-07. main에 기능 브랜치를 병합한 뒤 팀원에게 공유할 문서입니다. 이 문서 작성이 실제 병합이나 공개 서버 배포를 실행한 것은 아닙니다.

## 1. 이번 반영 내용

기존 HTML/CSS/JavaScript 화면에 있던 사진 조회·등록·좋아요·마이페이지 관리 기능을 Node.js 서버와 Supabase에 연결했습니다. 프런트엔드 프레임워크를 새로 도입하지 않았습니다.

| 페이지 | 반영 내용 |
|---|---|
| 메인 | 서버에서 기간·지도 범위별 사진 조회. 지도용 조회와 목록용 조회 분리, 목록 10장씩 더 보기, 사진 묶음·상세·좋아요 연결, 이전 요청이 늦게 도착해 최신 화면을 덮어쓰는 현상 방지 |
| 전체 사진 | 최신순·인기순 서버 정렬, 24장씩 더 보기, 상세 창, 조회 실패 재시도, 인기순 변동 시 같은 카드 중복 표시 방지 |
| 업로드 | 사진 압축 후 Storage 저장, 위치·설명·시각을 DB 저장, 등록한 사진을 메인·전체·마이페이지에서 조회 |
| 마이페이지 | 내 사진의 설명·장소명 수정과 삭제, 좋아요 취소, 닉네임 저장. 변경 뒤 내 목록·지도·통계·등급 갱신 |
| 로그인 | 기존 학교 인증 방식 유지, 세션을 외부 DB에 저장, 로그아웃 뒤 진행 중이던 조회가 세션을 되살리는 문제 수정 |

기존 지도 디자인, 캠퍼스 범위, 트랙패드 확대·축소 설정은 이번 작업에서 변경하지 않았습니다.

## 2. 서비스별 역할

```text
브라우저: HTML / CSS / JavaScript
        │ 우리 사이트의 /api/... 요청
        ▼
Node.js 22 + Express 5 서버
        ├─ PostgreSQL 연결 → Supabase DB
        │                    사진 정보·좋아요·프로필·로그인 세션
        ├─ Storage API    → Supabase Storage
        │                    실제 JPEG 사진 파일
        └─ 로그인 요청    → 기존 학교 Smart ID 인증 서버
```

배포 시 Render는 사이트와 API를 실행합니다. Supabase는 데이터와 사진을 보관합니다. Supabase Auth로 사용자 로그인을 구현한 구조는 아닙니다.

브라우저가 DB에 직접 접근하지 않습니다. 서버가 `pg`로 DB에 접근하고 공식 Supabase SDK로 사진 파일을 저장합니다. 키와 DB 비밀번호는 서버 환경변수로 관리합니다.

## 3. 사진 용량·압축·지원 형식

| 항목 | 실제 코드 기준 |
|---|---|
| 원본 선택 가능 형식 | JPG/JPEG, PNG, WEBP |
| 원본 선택 가능 용량 | 8 × 1024 × 1024 bytes 이하. UI에서는 8MB로 표시 |
| 선택 개수 | 현재 등록 폼은 한 번에 사진 1장 |
| 압축 위치 | 업로드 전 사용자 브라우저 |
| 저장 형식 | 원본 형식과 관계없이 JPEG로 변환 |
| 최대 해상도 | 긴 변 900px, 가로세로 비율 유지. 작은 이미지를 확대하지 않음 |
| JPEG 품질 설정 | `0.8`. 원본 용량의 80%로 만든다는 의미는 아님 |
| 투명 PNG | 흰색 배경 위에 그린 뒤 JPEG로 저장 |
| EXIF | 캔버스로 다시 저장하므로 원본의 촬영 기기·GPS 등 EXIF 메타데이터는 보존하지 않음 |
| 원본 보관 | 원본 파일은 서버에 별도 저장하지 않고 변환한 사진만 저장 |
| 서버 파일 제한 | 변환된 JPEG 5 × 1024 × 1024 bytes 이하, JPEG 시작 표식 검사 |
| Storage 버킷 제한 | `photos` 버킷, JPEG만 허용, 파일당 5 × 1024 × 1024 bytes |
| API 전송 | JPEG를 Base64 data URL로 변환하여 JSON에 포함 |
| 서버 JSON 요청 제한 | `8mb`. Base64 전송 시 파일보다 요청 크기가 커지는 점을 고려 |

원본이 6MB여도 그대로 6MB를 저장하지 않습니다. 900px 이하 JPEG로 변환한 결과가 저장됩니다. 최종 용량은 사진 내용에 따라 달라지므로 장당 고정 용량이나 최대 보관 장수를 보장하지 않습니다.

HEIC, GIF, 동영상, 다중 사진 등록은 현재 지원하지 않습니다. 아이폰 사진도 HEIC이면 JPG/PNG/WEBP로 바꾸어야 합니다.

## 4. 저장 공간과 무료 요금제

2026-11-07 공식 요금표 기준 Supabase Free는 DB 500MB, 파일 Storage 1GB입니다. 두 용량은 서로 다릅니다. [Supabase 공식 요금표](https://supabase.com/pricing)

- DB 500MB: 사진 설명·좌표·주소, 좋아요, 프로필, 세션과 인덱스 등에 사용.
- Storage 1GB: 실제 사진 파일이 차지하는 공간.
- 파일을 볼 때 발생하는 데이터 전송량도 저장 공간과 별도 제한이 있으므로 대시보드에서 함께 확인.
- 예시 계산: 실제 저장 결과가 평균 200KB라면 1GB는 대략 5,000장 수준입니다. 이는 실제 측정값이 아닌 단순 계산이며 다른 저장 파일·단위 차이·전송 한도는 별도입니다.
- 현재 앱에는 사용자별 사진 장수 제한이나 하루 업로드 횟수 제한을 구현하지 않았습니다. 저장소 한도에 도달하면 업로드가 실패할 수 있습니다.
- 무료 프로젝트는 1주일 비활성 시 일시 중지될 수 있습니다. 중요한 발표 전 프로젝트 상태를 확인합니다.

## 5. DB 테이블: 무엇을 저장하는가

테이블은 엑셀 시트처럼 같은 종류의 데이터를 행으로 모은 표입니다. 사진 한 장은 `photos`의 한 행이지만 실제 이미지 내용은 Storage에 있습니다.

### photos — 사진 정보

| 필드 | 의미 |
|---|---|
| `id` | 서버가 만든 고유 사진 ID |
| `author_id` | 등록한 사용자 구분값. 현재 학교 로그인 학번을 사용 |
| `image_url` | Storage에 있는 사진의 공개 주소 |
| `latitude`, `longitude` | 선택한 위도·경도 |
| `place_name`, `description` | 장소명·사진 설명 |
| `captured_at` | 사용자가 입력한 촬영 시각 |
| `uploaded_at` | 서버가 등록 시 부여한 업로드 시각 |
| `base_likes` | 예시 데이터의 기본 좋아요 수. 일반 업로드는 0 |
| `is_demo` | 예시 사진 구분값 |
| `deleted_at` | 삭제 상태를 기록한 시각. 일반 사진은 비어 있음 |

`captured_at`, `uploaded_at`은 현재 DB에서 text 타입이며, 서버가 `Date.toISOString()` 형식의 UTC 문자열로 통일하여 기록합니다. 팀원이 DB에 직접 넣을 때 다른 날짜 형식과 섞지 않아야 조회·정렬이 맞습니다.

### likes — 좋아요 관계

`user_id`와 `photo_id`를 저장합니다. 두 값을 합쳐 고유하게 관리하므로 같은 사용자가 같은 사진에 여러 번 좋아요를 등록해도 중복 증가하지 않습니다. 일반 사진의 좋아요 수는 실제 `likes` 행을 세어 계산합니다. 예시 사진은 `base_likes`가 추가됩니다.

### profiles — 프로필

`user_id`, `nickname`, `created_at`을 저장합니다. 닉네임은 재로그인해도 유지됩니다. 별도 로컬 비밀번호는 저장하지 않습니다. 기존 사용자에게 표시되는 가입일은 새 프로필을 처음 생성한 시각이며, 학교 입학일이나 예전 사이트 가입일을 복원한 값은 아닙니다.

### sessions — 로그인 상태

`sid`, `data`, `expires`를 저장합니다. 쿠키에는 세션 식별 정보를 사용하고 서버가 DB에서 로그인 사용자를 확인합니다. 학교 비밀번호와 학교 `sToken`을 세션에 저장하지 않습니다.

## 6. 로그인과 권한

현재 로그인은 우리 화면에서 학번·비밀번호를 입력하면 Node 서버가 기존 학교 Smart ID 인증 서버에 전달해 확인하는 방식입니다. 공식 OAuth/리다이렉트 SSO 연동이라고 설명하면 안 됩니다. 학교 비밀번호는 인증 처리 시 서버를 거치지만 우리 DB에는 저장하지 않습니다.

| 동작 | 권한 |
|---|---|
| 메인·전체 사진·상세 조회 | 비로그인도 가능 |
| 사진 등록·좋아요·좋아요 취소 | 로그인 필요 |
| 내 사진·내 좋아요·프로필 조회 | 로그인한 본인 |
| 사진 설명·장소명 수정 및 삭제 | 사진 작성자 본인만 |
| 닉네임 수정 | 로그인한 본인만 |
| 학교 비밀번호 변경 | 학교 사이트에서 처리. 우리 서비스에는 변경 API 없음 |

프런트엔드에서 버튼을 숨기는 것에 더해 서버 SQL에서도 작성자와 로그인 사용자가 같은지 확인합니다. 다른 사람 사진의 수정·삭제 요청은 404로 처리합니다. 학번은 공개 사진 응답에서 제외하고 본인의 `/api/me`에서만 계정 정보로 확인합니다.

세션 쿠키 설정은 7일이며 HttpOnly, SameSite=Lax를 사용합니다. 배포 환경은 Secure 쿠키와 HTTPS를 사용합니다. 로그인 성공 시 세션을 새로 만들고 로그아웃 시 DB 세션과 쿠키를 제거합니다.

DB의 네 테이블은 RLS를 켜고 `anon`·`authenticated` 역할의 테이블 권한을 회수했습니다. 브라우저용 Supabase 키로 직접 테이블을 읽고 쓰는 설계가 아니며, 서버에서 권한을 확인합니다. `photos` Storage 버킷은 공개이므로 사진 URL을 알면 비로그인도 이미지를 볼 수 있습니다. 로그인 전용 비공개 앨범은 아닙니다.

공개 배포에서는 `ALLOW_TEST_LOGIN=false`이며 코드상 production에서는 개발 테스트 계정으로 로그인할 수 없습니다.

## 7. 조회와 입력 기준

- 메인의 시간 필터는 **촬영 시각이 아니라 업로드 시각**을 기준으로 합니다. 화면은 한국 시간으로 표시하고 서버에는 UTC ISO 시각을 보냅니다.
- 업로드 위치는 숭실대 캠퍼스 범위 안이어야 합니다. 위도 37.4938~37.4990, 경도 126.9538~126.9612입니다.
- 메인 옆 목록은 10장, 전체 사진은 24장씩 불러옵니다. 다음 페이지는 `nextCursor`로 이어 받습니다.
- 지도용 API는 목록 10장 제한을 사용하지 않으며 한 요청에서 최대 5,000개를 반환합니다. 초과하면 `truncated=true`와 확대 안내를 표시합니다.
- 최신순은 업로드 시각 내림차순, 같은 시각은 ID 내림차순입니다. 인기순은 좋아요 내림차순 후 최신순입니다.
- 인기순은 실시간 좋아요 수를 사용하므로 다른 사용자의 동작으로 순위가 바뀔 수 있습니다. 이어 보기에서 중복은 제거하지만 모든 사진을 고정된 스냅샷으로 보장하는 구조는 아닙니다. 새로고침하면 현재 순위로 다시 조회합니다.
- 사용자 사진·좋아요 목록은 현재 API 페이지를 반복 조회하여 모으는 구조입니다. 대량 데이터에서 마이페이지도 화면 단위 페이지 조회로 바꿀 여지가 있습니다.

입력 길이는 화면과 API가 일부 다릅니다. 업로드 화면은 장소 60자·설명 160자이며, 서버 등록은 장소 100자·설명 1,000자까지 잘라 저장합니다. 마이페이지 수정은 장소 100자·설명 1,000자이며 초과 시 거부합니다. 닉네임은 공백 제거 후 2~12자입니다.

## 8. 사진 저장·삭제 순서와 오류 처리

등록은 로그인/좌표/입력 확인 → Storage에 이미지 저장 → DB에 사진 정보 저장 순서입니다. DB 저장에 실패하면 방금 저장한 파일을 정리하도록 구현했습니다. 다만 이때 파일 정리도 실패하는 경우까지 추적하는 업로드용 영구 재시도 큐는 없습니다.

삭제는 다음 순서입니다.

1. 본인 사진인지 확인하고 `deleted_at`을 기록합니다.
2. 지도·전체 사진·내 사진·좋아요·기간 계산에서 즉시 제외합니다.
3. Storage 파일과 관련 좋아요, 사진 DB 행을 정리합니다.
4. 파일 정리가 실패하면 삭제 상태를 DB에 남겨 서버 시작 시와 60초 간격으로 다시 정리합니다. 한 번에 최대 100장입니다.

DB와 Storage를 하나의 트랜잭션으로 묶는 구조는 아닙니다. 삭제 API 성공은 화면에서 제거된 상태를 뜻하며, 저장소 장애 시 파일의 물리적 삭제는 늦어질 수 있습니다. 공개 이미지 URL의 캐시까지 즉시 제거된다고 보장하지 않습니다.

DB/Storage 연결 실패를 예시 사진으로 대체하지 않고 오류로 표시합니다. 주요 목록에는 재시도 버튼을 연결했습니다.

## 9. API 목록

| 메서드·주소 | 역할 |
|---|---|
| `POST /api/login` | 학교 계정 확인 및 세션 생성 |
| `POST /api/logout` | 로그아웃 |
| `GET /api/me` | 본인 프로필 조회 |
| `PATCH /api/me` | 닉네임 수정 |
| `GET /api/photos/extent` | 전체 업로드 시각의 시작·끝 |
| `GET /api/map/photos` | 기간·지도 범위의 사진 |
| `GET /api/photos` | 최신순/인기순 사진 목록 |
| `POST /api/photos/search` | 선택한 사진 묶음을 ID 기준으로 조회 |
| `GET /api/photos/:id` | 사진 상세 |
| `POST /api/photos` | 사진 등록 |
| `PATCH /api/photos/:id` | 내 사진의 설명·장소명 수정 |
| `DELETE /api/photos/:id` | 내 사진 삭제 |
| `PUT /api/likes/:id` | `{liked:true}` 등록 / `{liked:false}` 취소 |
| `GET /api/likes` | 좋아요 집계와 내 좋아요 ID |
| `GET /api/my/photos` | 내 사진 목록 |
| `GET /api/my/likes` | 내 좋아요 사진 목록 |
| `GET /api/health` | 서버 상태·DB 종류 확인 |

목록은 `photos`, `total`, `nextCursor`를 반환합니다. `limit`은 기본 10, 최대 100입니다. 기간 `start/end`, 범위 `south/west/north/east`, 정렬 `order=latest/popular`, 다음 페이지 `cursor`를 사용합니다. 선택 묶음의 ID 조건은 지도 경계보다 우선하지만 기간 조건은 유지합니다.

주요 오류는 잘못된 입력 400, 로그인 필요 401, 없는 사진/수정 권한 없는 사진 404, 요청 본문 초과 413, 서버 처리 실패 500입니다. 학교 인증 연결 실패는 502, 시간 초과는 504로 구분합니다.

## 10. 로컬 실행과 배포

Node는 **22.12 이상 23 미만**을 사용합니다.

```sh
npm ci
npm start
```

기본 주소는 `http://localhost:3000`이며 `PORT`로 바꿀 수 있습니다. API가 있는 서비스이므로 Python 정적 서버나 GitHub Pages만으로 전체 기능을 실행할 수 없습니다.

새 Supabase 프로젝트에는 `supabase/migrations/202611060001_main_photos.sql`과 `202611060002_photo_management.sql`을 번호 순서대로 적용합니다. 같은 프로젝트를 쓰는 팀원은 이미 적용된 SQL을 매번 실행할 필요가 없습니다. 연결한 개발 프로젝트에는 두 파일을 적용했습니다.

| 서버 환경변수 | 의미 |
|---|---|
| `DATABASE_URL` | Supabase Session pooler의 PostgreSQL 주소. 비밀번호 특수문자는 URI 인코딩 필요 |
| `SUPABASE_URL` | 프로젝트 API 주소 |
| `SUPABASE_SERVICE_ROLE_KEY` | 서버 전용 비밀키. 기존 service_role 또는 지원되는 새 Secret key |
| `SUPABASE_STORAGE_BUCKET` | `photos` |
| `DATABASE_SSL_CA` | DB TLS 검증에 필요한 공식 CA 인증서. 이번 연결에서는 설정해서 사용 |
| `SESSION_SECRET` | 세션 서명용 긴 랜덤 값. 서버 재시작 때 같은 값을 유지 |
| `NODE_ENV` | 배포는 `production` |
| `ALLOW_TEST_LOGIN` | 배포는 `false` |
| `SEED_DEMO_PHOTOS` | 실제 프로젝트는 `false` |
| `PORT` | 로컬/호스팅의 서버 포트 |

`.env.example`을 참고해 `.env`를 만들고 값은 별도로 전달받습니다. `.env`, DB 비밀번호, Secret key를 GitHub나 팀 공유 문서에 붙이지 않습니다. 학교 비밀번호도 팀원에게 공유하지 않습니다.

외부 DB 없이 로컬 개발을 하면 `storage/`의 SQLite와 파일을 사용할 수 있지만, Supabase 데이터와 자동 동기화·이관되지는 않습니다. 배포 모드에서는 외부 저장소 설정이 없으면 서버가 시작되지 않습니다. DB 연결은 인증서 검증을 켠 TLS, 최대 연결 5개, 연결 대기 10초·쿼리 제한 15초로 설정했습니다.

**main 병합과 공개 서버 배포는 별도입니다.** 현재 `render.yaml`은 배포 브랜치가 `feature/login-server`로 되어 있으므로 main 기준 배포 시 `main`으로 바꾸고 Render 서비스의 실제 연결 브랜치도 확인해야 합니다. `DATABASE_SSL_CA`도 Render 환경변수에 별도로 설정해야 하며, 현재 Blueprint에는 이 항목이 자동 추가되어 있지 않습니다.

Render Free는 15분 동안 들어오는 요청이 없으면 쉬고 다음 접속 시 다시 시작합니다. 로컬 파일은 재시작/재배포/휴면에 따라 사라질 수 있습니다. 그래서 DB·사진·세션을 Supabase에 보관하도록 분리했습니다. 단, 무료 서비스 자체의 휴면·사용량 한도는 별도로 존재합니다. [Render 공식 안내](https://render.com/docs/free)

## 12. 검증 범위와 남은 확인

전체 자동 테스트 56개가 통과했습니다. SQLite HTTP API, embedded PostgreSQL 스키마/쿼리, 실제 HTML을 읽는 jsdom 테스트로 소유권·수정·삭제·좋아요 취소·닉네임 유지·정렬·더 보기·오류 재시도를 확인했습니다. 실제 Supabase에도 임시 JPEG 한 장을 올려 읽기·수정·좋아요·취소·삭제를 확인하고 테스트 사진과 세션을 정리했습니다.

자동 테스트는 실제 Supabase 설정과 분리된 DB를 사용하므로 사용자 사진을 지우지 않습니다. 학교 인증은 테스트에서 외부 경계를 대체하며 실제 비밀번호로 자동 로그인하지 않습니다.

팀원이 실제 브라우저에서 확인할 사항:

1. 두 계정으로 로그인하여 자기 사진만 수정/삭제되는지 확인.
2. JPG/PNG/WEBP 등록, 8MB 초과/지원하지 않는 형식 거부, 건물/지도 위치 선택 확인.
3. 등록→메인→전체 사진→마이페이지, 수정·좋아요 취소·삭제 후 새로고침까지 확인.
4. 닉네임 저장 후 재로그인, 로그아웃 뒤 쓰기 차단 확인.
5. 지도 타일·트랙패드·사진 묶음·날짜 필터·실제 화면 배치 확인. 브라우저 연결 도구 불가로 이 부분은 직접 조작 자동 검증하지 못함.
6. main 기준 Render 배포 뒤 HTTPS 로그인과 학교 서버 접속, 휴면/재시작 후 사진·좋아요·세션 유지 확인. 배포 검증은 아직 남아 있음.
7. 보조 문구 중 업로드 파일 선택 영역의 “이 브라우저에 저장”은 오래된 문구가 남아 있음. 실제 저장은 Supabase이며 문구 수정 필요.

현재 범위에 없는 기능: 개인 이메일 회원가입과 별도 학교 이메일 인증, 공식 OAuth SSO, 학교 비밀번호 변경, 이미지 원본 보관, 신고/관리자 검수, 업로드 횟수 제한, 자동 백업·복원 절차 구축. 해당 기능까지 완료했다고 설명하지 않습니다.

오류를 공유할 때는 페이지 주소·클릭한 버튼·재현 순서·기대 결과·실제 결과를 남기고 비밀번호·비밀키는 제외합니다.
