# 메인페이지 백엔드

사용자가 승인한 방향: 기존 Node/Express 로그인 서버를 유지하고 사진 메타데이터·좋아요·세션은 Supabase PostgreSQL, 사진 파일은 Supabase Storage로 분리한다. Supabase 프로젝트는 아직 없으므로 로컬에서 동일 API를 SQLite로 검증하고 연결 준비까지 완료한다. 학교 로그인 방식과 지도 감도·범위·화면 디자인은 바꾸지 않는다.

## 접근 방식
- 선택: Node 서버 + 외부 PostgreSQL/Storage. 기존 로그인 세션과 화면 재사용, Render 중지와 저장 데이터 분리.
- SQLite/파일만 유지: 구현은 간단하지만 무료 Render에서 데이터 유실 문제를 해결하지 못함.
- 브라우저에서 Supabase 직접 접근: 기존 학교 로그인 세션과 다른 인증 경계가 필요하여 이번 작업에서 제외.

## 계약
- `/api/map/photos`: 업로드 기간·지도 경계의 사진 조회. 목록의 10장 제한을 적용하지 않음. 5,000장 안전 한도 도달 시 truncated를 명시.
- `/api/photos`: 동일 조건 또는 선택 묶음 IDs, 최신순 10장, 업로드 시각+ID 복합 커서, 전체 건수와 다음 커서 반환. 기존 전체 사진 페이지는 page 조회 반복으로 호환.
- `/api/photos/:id`: 단일 사진 상세. 학번/작성자 ID 비공개.
- 기존 사진 등록·내 사진·좋아요 API는 동일 저장소를 이용. 좋아요는 세션 사용자만, 중복 불가. 예시 사진도 서버에서 한 번만 공급하고 실제 사진과 구분.
- PostgreSQL 연결값 일부만 있거나 배포 환경에 외부 저장소가 없으면 조용히 로컬로 대체하지 않고 시작 실패. 비밀키와 DB URI는 서버 환경변수에만 저장.
- SQL 스키마는 별도 명시적 적용. public 테이블은 RLS 활성화, anon/authenticated 직접 접근 차단. Node의 서버 DB 계정만 접근. 사진은 공개 버킷, 파일 쓰기 권한은 Node 서버만 보유.
- Supabase 없는 로컬은 SQLite/파일 사용. 기존 SQLite 사진을 보존하는 추가 칼럼 마이그레이션. 서버 재시작 후 세션·사진·좋아요 검증.
- 메인화면은 시간 조건과 지도 이동에 따라 서버 조회. 오래된 응답은 무시. 실패 시 오류·재시도 표시, 예시 데이터로 오류를 숨기지 않음.

## 검증 범위
실제 SQLite + HTTP로 기간/경계, 50장 목록과 모든 마커, 커서 중복, 상세 404, 익명 권한, 좋아요 멱등성, 재시작 보존을 검증. PostgreSQL 연결·Storage 실서비스·Render 재시작 보존은 계정 생성 뒤 통합 검증 필요. 코드 준비를 서비스 연결 완료로 표현하지 않는다.
